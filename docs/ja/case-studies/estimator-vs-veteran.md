# Estimator vs. Veteran: スコープを統制した回顧的比較

## 証拠の境界

このケーススタディは、公開されている[トラッキング Issue #10](https://github.com/tshimada-dev/codex-config/issues/10)の比較記録を再構成します。元の非公開要件、workbook、社名、顧客名、価格、source fileは使いません。公開記録だけでは新たなbenchmark実行はできませんでした。

したがって、これは公開された集計値の回顧的な監査であり、独立した再現でも、ある見積もり方式が一般的に優れているという証拠でもありません。

## 問い

元の記録では、ベテラン見積もりがAIなし170人日、AIあり115人日だったのに対し、estimator SkillはAI考慮値450人日を出しました。その後、より薄い実装スコープを与えると、Skillは人手175人日、WBS最頻値189人日を出しました。

有用な問いは単に「どの数値が勝ったか」ではありません。

1. スコープを揃えた後、見えていた不一致のどれだけが消えるか。
2. どの比較が真にlike-for-likeか。
3. どの原因帰属を公開証拠から再計算できるか。
4. どの不確実性が残るか。

## 計算前に固定する再構成ルール

結果を見た後に都合のよい解釈を選ばないよう、この文書では次のルールを使います。

1. Issue #10に明示された値だけを使う。
2. 各値の公開されたbasisを維持する。初回のAI考慮450を人手工数へ、スコープ調整後の人手175をAI考慮工数へ読み替えない。
3. 175対170を主要なlike-for-likeの人手工数比較とする。
4. 175対115は、報告されたAI補正残差の診断だけに使い、独立手法の比較とはしない。
5. すべての算式と分母を示す。
6. 公開記録に内訳がない原因帰属は「source報告値、独立再現不可」と明記する。
7. この1件のサニタイズ済みcaseから一般化しない。

## 公開された観測値

| 観測 | 人日 | 公開記録上のbasis | 比較可能な対象 |
|---|---:|---|---|
| Skill初回結果 | 450 | 薄いスコープを明確化する前のAI考慮見積もり | 追加の内訳なしでは、どちらのベテラン値とも直接比較不可 |
| ベテラン人手見積もり | 170 | 人手工数 | スコープ調整後の人手175 |
| ベテランAI考慮見積もり | 115 | AI考慮工数 | 報告された残差の診断比較のみ |

| スコープ調整後WBS最頻値 | 189 | WBS most-likely | 補助的な監査値。選択した比較中心ではない |

Source: [Issue #10「重要な実証結果」](https://github.com/tshimada-dev/codex-config/issues/10)。

## 統制した再構成手順

1. 上記の公開観測値を固定する。
2. 450と170のAI basisが同じだと仮定せず、初回の不一致を記録する。
3. 既に報告された介入、すなわちベテランのより薄いスコープ前提を導入する。
4. スコープ調整後の人手175をベテラン人手170と比較する。
5. 175と115を使うAI残差はbasis不一致の注意を残し、別に計算する。
6. Sourceの「約85%」という原因帰属を公開集計値に照らして監査する。
7. このcaseを普遍的な精度主張に変えず、限界と改善作業を記録する。

## 再計算可能な結果

### 初回の可視的な不一致

- ベテラン人手見積もりに対する比: `450 / 170 = 2.647`、約`2.65倍`。
- ベテラン人手見積もりに対する超過率: `(450 - 170) / 170 = 164.7%`。
- ベテランAI考慮見積もりに対する比: `450 / 115 = 3.913`、約`3.91倍`。

これらはsourceが約3〜4倍の不一致と表現した理由を示しますが、分母が重要です。450は170の2.65倍、115の3.91倍です。

### スコープ調整後のlike-for-like人手見積もり

- 絶対差: `175 - 170 = 5`人日。
- 相対差: `(175 - 170) / 170 = 2.9%`。

公開集計値の範囲では、スコープ調整後の人手見積もりはベテラン人手見積もりに近接しました。これは、このcaseでスコープ解釈が人手見積もりの可視的な不一致を大きく左右した、という限定的な結論を支持します。

### 報告されたAI補正残差

- 絶対差: `175 - 115 = 60`人日。
- ベテランAI考慮値を分母にした相対差: `(175 - 115) / 115 = 52.2%`。
- 175から115へ到達するための削減率: `(175 - 115) / 175 = 34.3%`。

115を分母にすればsourceの「約50%」は再計算できます。ただし175は人手工数、115はAI考慮工数なので、これは診断比較のままです。

### 報告された85%の原因帰属を独立再現できない理由

公開Issueは、元の乖離の約85%がスコープ解釈に起因すると報告していますが、行別内訳やその割合の算式を公開していません。

単純な集計gap closureなら次のようになります。

`((450 - 170) - (175 - 170)) / (450 - 170) = 98.2%`

この98.2%を報告された85%の代わりに使ってはいけません。この計算は初回のAI考慮値と、スコープ調整後の人手値をまたぐため、スコープ以外も変えています。防御可能な記録は次のとおりです。

- `約85%`: source報告の原因帰属。公開集計値からは独立再現不可。
- `98.2%`: 機械的に見える集計gap closure。純粋なスコープ原因帰属ではない。

## この記録が支持する結論

公開証拠は、次の3つの限定的な結論を支持します。

1. より薄いスコープを与えた後、Skillの人手見積もり175はベテラン人手170に対して5人日、2.9%の差だった。
2. スコープ解釈は元の可視的な不一致の主要因だったが、正確な85%の原因帰属はサニタイズ済み公開データから独立再構成できない。
3. 残るAI補正比較は115を分母にすると約52%上であり、スコープに反応するAI区分を厳格にする動機になった。

このcaseは、一般的な見積精度、因果的優位性、他案件での期待性能を確立しません。

## この発見につながる改善

- [Issue #4](https://github.com/tshimada-dev/codex-config/issues/4)は、AI補正を行レベル化し、係数権限を固定し、スコープ駆動の再分類と保守性警告を追加しました。現在は完了しています。
- [Issue #3](https://github.com/tshimada-dev/codex-config/issues/3)は、単発比較をestimate-to-actualの測定証拠へ置き換えるために残る較正ループ作業です。
- 見積もり前のscope gateも重要なfollow-upです。実装方式、明示除外、受入責任、テスト責任を見積もり前に明確にする必要があります。

## 再現チェックリスト

非公開入力なしで、この文書の算術を再現できます。

1. Issue #10から5つの公開観測値を読む。
2. 上記の式をそのまま計算する。
3. 175対170だけがlike-for-likeの人手比較であることを確認する。
4. 85%の原因帰属には公開内訳がなく、source報告値のままであることを確認する。
5. 社名、個人、価格、非公開workbook、顧客fileに依存する記述がないことを確認する。

リポジトリのvalidation testは、これらの値、算式、link、証拠label、機密境界を固定し、後の編集で主張が密かに強くならないようにします。
